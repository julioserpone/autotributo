- F3-07: aritmética fiscal y proporcionalidad de IVA. Nuevo value object `App\Domain\Shared\Values\Money` sobre `brick/money` (dependencia directa `^0.15`): importes en centavos enteros, entrada por `cents()` u `ofDecimal()` con redondeo HALF_UP en el borde, salida por `toCents()`/`decimal()`, `plus`/`minus`/`multipliedBy` y comparación por valor; nunca `float`. `App\Domain\Fiscal\Services\Proportionality` calcula el factor de ventas con tarifa 0 % sobre el total con 6 decimales (`RoundingMode::HalfUp`), expone `complement()` como `1 − factor` para que ambas caras sumen `1.000000` exacto y `apply()` para repartir un importe (p. ej. el IVA de compras comunes) con redondeo a centavos; un período sin ventas devuelve `0.000000` y las ventas negativas se rechazan. ### Fixed
- Staging: la caja "En curso" ya no arrastra líneas viejas. La salida de npm, Vite, Composer y `docker compose` usa `\r` y códigos ANSI para repintar la misma línea (progreso), y el panel los trataba como líneas nuevas: cientos de `transforming…` desplazaban la salida real y seguían visibles cuando el proceso ya había avanzado a `php artisan migrate`. Ahora se conserva solo el estado final de cada línea física, se limpian los códigos de control y se descartan las repeticiones consecutivas; el resultado se cachea por tamaño de log para no recalcularlo en cada repintado.
- Staging: `create` ya no aborta por un timeout de SSH transitorio. Una instancia recién arrancada puede tardar en aceptar conexiones mientras termina cloud-init, y con `ConnectTimeout=10` el `ssh` del aprovisionamiento fallaba con `Operation timed out` dejando la máquina encendida y el proceso a medias. Ahora los `ssh` remotos usan `ConnectTimeout=20` con keepalive y se reintentan hasta 5 veces (10 s entre intentos) solo cuando el fallo es de transporte (código 255), sin reintentar errores del comando remoto; `wait_ssh` espera 90 s y `git clone` usa `--depth 1`. Los mensajes de fallo de las etapas 3 y 4 indican el ID de la instancia que sigue encendida y cómo destruirla.
- Staging: `destroy` ya no destruye el respaldo local cuando falla la descarga. `backup_remote` escribía con `>` directamente sobre `~/.config/autotributo/duckdns.env`, así que un `ssh` fallido dejaba el token en **0 bytes** (y el `scp` del `.env` se ignoraba con `|| true`). Ahora descarga a temporales, exige contenido en ambos archivos y solo entonces reemplaza `staging.env` y `duckdns.env`; si algo falla, la etapa queda en aviso con el motivo y el respaldo anterior intacto. El resumen final imprime el motivo bajo la etapa (`↳ …`) en lugar de dejar `AVISO` sin explicación. `create` valida `-s` (no vacío) en ambos respaldos y aborta en la etapa 1 con un mensaje que indica qué escribir en `duckdns.env`.

- F4-06: el progreso del monitor contaba los archivos `missing` e `invalid` como procesados, así que un run en `downloading` mostraba 92 % aunque los XML todavía no estuvieran en S3. Ahora solo cuentan `available`/`processed`, el progreso se expresa por etapa y un run activo nunca llega a 100 % (el 100 se reserva para `completed`/`partial`); un run fallido sin comprobantes muestra 0 %, no 100 %. `SriSyncRun::progressPercentage()` también incluye `updated` y topa en 99 mientras el run siga activo.
- F4-06: los XML que llegan a S3 después de que su bloque de importación ya corrió quedaban como `available` sin procesarse. `FinalizeSriRun` ahora reconcilia contra S3 e importa esos archivos antes de cerrar el run, y el detalle muestra una leyenda de los estados de archivo (En S3 = XML en el bucket, aún no importado).
- F4-06: `forzar` ahora se persiste en el run (`force`) y la importación omite la comprobación de `xml_sha256` cuando está activo, por lo que una re-descarga forzada re-importa los comprobantes (resultado `updated`) en vez de marcarlos `skipped`, aunque el XML sea idéntico. Así una sincronización forzada repara importaciones anteriores sin impacto fiscal, porque el documento autorizado no cambia.
- F2-07: `ParseSriRun` marcaba `incomplete_package` a todo tipo solicitado que no produjera lote, aunque el manifiesto del robot solo lista las descargas con resultados. Eso provocaba un aviso transitorio de «paquete incompleto» en runs normales (p. ej. sin notas de crédito en el período), que `FinalizeSriRun` borraba después. Ahora solo es incompleto un tipo declarado en el manifiesto que quedó sin lote, y el detalle no muestra errores del run mientras siga activo.
- F4-06: el historial de sincronizaciones se reemplazaba por «Cargando…» en cada refresco de 5 s, así que la lista parecía vaciarse mientras un run estaba activo. Ahora `fetchRuns` solo activa `loading` en la primera carga (el refresco es silencioso) y el historial mantiene la lista en pantalla. Cada item muestra el ID completo y el período en la misma línea en escritorio (`ID … | Periodo …`) y en tres líneas en móvil (ID, período y documentos consultados).
- F4-06: el monitor ofrecía la guía de remisión (`06`) y el robot del portal no la soporta: una sincronización con ese tipo fallaba completa con `robot_failed`. Se añade `SriDocumentType::syncableCodes()` (01, 03, 04, 05, 07), se usa como valor por defecto y en la validación de `POST /api/v1/sync-runs` (la guía de remisión responde `422`), y el formulario ya no la ofrece.
- F4-06: `monthsBetween` construía los períodos con `Date` y los interpretaba como UTC, así que en Ecuador un rango de octubre pedía septiembre. Ahora la aritmética es con enteros y el rango se valida (invertido o inválido devuelve vacío).
- F4-06: el run fallido muestra el `error` que devuelve el robot (normalizado y acotado a 500 caracteres) en lugar del mensaje genérico, para que el monitor explique la causa real.
- F4-06: cuando el robot publicaba los XML de un período pero no un TXT/JSON de claves válido (el portal devolvió el listado sin claves), el run se quedaba en `downloading` hasta `robot_timeout` aunque la descarga hubiera terminado. `RecoverSriRunFromS3` pasa el run a `parsing` cuando hay XML de todos los períodos y `ParseSriRun` arma el lote con las claves de los nombres de archivo, validando tipo y período (el RUC de la clave es el emisor/proveedor en los recibidos, no el de la empresa).
- F4-06: los XML que publica el robot son la respuesta completa de autorización (`autorizacion` con el comprobante en CDATA); `S3SriXmlRecovery::contents()` desenvuelve el comprobante interior antes de parsear.
- F4-06: el comprobante real usa `DOLAR` como moneda; el adaptador lo normaliza a `USD` para el campo `char(3)` de la tabla `invoices`.
- F2-07: `PeriodBatchBuilder` ya no descarta claves cuyo RUC emisor difiere del RUC de la empresa, porque en los comprobantes recibidos ese RUC es el del proveedor. La empresa está garantizada por la carpeta del bucket y por el manifiesto.
- F2-09: el progreso en vivo no llegaba a Reverb en Docker local porque `app`/`queue`/`scheduler` usaban `REVERB_HOST=localhost`; ahora la red interna resuelve `reverb` y el navegador conserva `VITE_REVERB_HOST`. Además, `SriSyncProgressUpdated` resuelve la empresa sin `TenantScope`, para que el webhook del robot (sin contexto de tenant) también pueda publicar el evento.
- Script `scripts/staging/ec2-control.sh`: al detener staging se hace polling del estado de RDS en lugar de usar el waiter inexistente `db-instance-stopped` de AWS CLI 2.x.
- Validación del manifiesto S3 y de los archivos de claves antes de marcar un run como `parsing`.
- Reconciliación periódica ahora intenta recuperar el paquete desde S3 (incluidos XML) en cada pasada, para que un run con TXT/JSON inválidos pero con XML publicados avance a `parsing` sin esperar al cierre por inactividad. El mensaje de error del TXT aclara los bytes declarados por el manifiesto frente a los del archivo, y el texto de error en la lista de archivos del monitor usa el mismo color que los nombres de archivo para ser legible.
- El parser del TXT del robot soporta el formato real publicado (TSV con encabezado y columna `CLAVE_ACCESO`) además del formato histórico de una clave por línea, por lo que los TXT tabulares ya no se marcan como “sin claves válidas”.
- F2-06/F2-07: la importación ya no falla cuando las filas de los XML aún no están registradas en `sri_sync_run_files` (carrera entre reconciliación y jobs de importación); `ImportSriKeys::fromS3()` construye la ruta S3 en memoria a partir de la clave de acceso y sigue verificando manifiesto/período. Además, `AwaitSriRobotResultJob` ahora permite todos los reintentos de sondeo (`tries = attemptsRemaining + 1`), evitando que el run se quede en `downloading` sin recuperar el paquete desde S3.
- `ReconcileSriRun` ignora un manifiesto generado antes de que se invocara el run (tolerancia de 5 min), evitando que una re-sincronización reutilice archivos viejos de S3 cuando el robot falló en la nueva ejecución. El timer del detalle del run muestra “Tiempo de ejecución del robot” cuando termina.
